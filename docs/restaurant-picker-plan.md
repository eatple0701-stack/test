# 식당을 등록부에서 고르게 하기 — 작업 계획

**작성 2026-09-01.** 아직 착수 전. 근거와 범위만 먼저 적어 둡니다.

---

## 왜 지금 이 작업인가 — 실사례가 나왔습니다

2026-09-01 19:55, 호스트에게 실제로 발송된 알림 메일 본문:

```
조강민 asked to sit at your table — 2026-09-03 19:00, sd.
```

**식당 이름이 `sd`입니다.** 상 차리기 폼의 "어느 식당인가요? (선택)"이
`<input type="text">`라 누군가 두 글자를 쳤고, 그 값이

1. 밥상 카드 (`sd에서 만나요`)
2. 밥상 상세 페이지
3. **호스트에게 나간 이메일**

세 곳에 그대로 찍혔습니다. 앱이 사람에게 보내는 유일한 메일에
의미 없는 두 글자가 장소로 들어간 것입니다.

이건 데이터 품질 문제가 아니라 **연결 안 된 문제**입니다. 등록부 8,136곳에
영어 이름·좌표·카테고리·영업시간·메뉴가 이미 있고, 이 화면에 하나도
붙어 있지 않습니다.

## 지금 잃고 있는 것

자유 입력이라 밥상이:

- 장소 페이지로 **링크를 못 겁니다**
- 지도에 **핀을 못 찍습니다** (좌표가 없음)
- **영업시간**을 못 보여줍니다 — 밥상 시각에 문을 여는지 아무도 모릅니다
- **택시 카드**(한국어 이름·도로명 주소 복사)를 못 씁니다
- 외국인 여행자에게 **영어 이름**을 못 줍니다

전부 이미 만들어 둔 데이터입니다.

## 범위

1. `<input type="text">` → **등록부 검색 선택기**
2. 고르면 이름·좌표·카테고리가 자동으로 채워짐
3. **"함께 정하기"는 그대로 남깁니다** — 호스트가 아직 안 정했을 수 있고,
   그건 정직한 상태입니다
4. 검토 요청: **식당을 먼저 고르면 요리·카테고리가 추론되는 순서**도
   같이 보기. 사람은 "이 집 가고 싶다"로 정하지 "요리 분류"로 정하지 않습니다

## 같이 걸린 것 — 요리 10개만 선택 가능 (**해결됨 2026-09-02** — 아래는 당시 기록)

> 카탈로그가 24개로 채워졌고, 밥상 탭에 요리 이름 검색이 생겼습니다.
> 아래 진단은 그날 그대로 두고, "번들에 24개가 다 있다"는 문장은 절반만
> 맞았다는 것만 적어둡니다 — 이름·로마자·한 줄 설명만 있었고, 폼이 필요로
> 하는 기록(7개 언어 × 4개 산문, 사실 필드)은 10개에만 있었습니다. 코드
> 문제가 아니라 콘텐츠 문제였고, 그래서 하루가 걸렸습니다.

번들에 요리 24개가 다 있는데(떡볶이·순대·튀김·비빔밥·찜닭·해물찜·산낙지·
육회·닭발·갈비·닭한마리·전골 포함, 로마자와 설명까지) 상 차리기 폼은
**10개만** 보여줍니다. 홈에서 6개 카테고리로 24개를 광고하는데 **떡볶이
밥상은 이 앱에서 열 수가 없습니다.**

방향: 홈의 6개 카테고리를 대분류로 쓰고(이미 만들어져 있음) 24개를 그 안에
펼치기. 중식·양식·일식 같은 대분류는 **넣지 않습니다** — 이 서비스의 전제가
"혼자 주문할 수 없는 **한국** 음식"이고 계획서도 그렇게 쓰여 있습니다.
채식·할랄은 카테고리가 아니라 **가로지르는 필터**로.
