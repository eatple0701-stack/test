# 파일럿 이용자 수 — `profiles` 행 수를 그대로 쓰면 안 되는 이유

**작성 2026-09-01.** 결과보고서(9/20)에 이용자 수를 쓰실 분에게 넘기는 자료입니다.

> **결론부터**: `profiles` 테이블에 **237행**이 있지만, 실제 도착 횟수는
> **약 91회**입니다. 행 수를 그대로 쓰면 **2.6배 부풀린 숫자**를 KF에
> 보고하게 됩니다.

## 1. 무슨 일이 있었나

2026-07-29부터 2026-09-01까지, 앱은 **첫 방문 한 번에 익명 계정을 여러 개**
만들었습니다.

부팅 중에 여러 화면이 동시에 "지금 사용자가 누구냐"를 묻는데, 첫 방문이면
전부 "세션 없음"을 보고 전부 익명 로그인을 호출했습니다. 호출된 만큼 계정이
생기고, 그만큼 `profiles` 행이 생깁니다. 토큰은 하나만 남으므로 나머지는
**아무도 돌아갈 수 없는 고아 행**입니다.

- 유입: `1aac1cd` (2026-07-29) — 처음 작성될 때부터
- 수정: `eff119f` (2026-09-01)
- 실제 데이터가 쌓인 구간: **2026-08-03 ~ 2026-09-01**
  (첫 행이 8/3이므로 7/29~8/2에는 트래픽이 없었습니다)

수정 후 프로덕션 실측: 첫 방문 → 로그인 1회, 행 1개.

## 3. 어떻게 셌나

행 삭제는 하지 않았습니다. **`created_at` 타임스탬프만** 읽어서 세었습니다
(이름·국적·언어는 조회하지 않았습니다).

같은 페이지 로드에서 만들어진 계정들은 **밀리초 단위로 붙어서** 생성됩니다.
반면 서로 다른 방문은 최소 수십 초, 보통 몇 시간에서 며칠 떨어져 있습니다.
그래서 "연속한 두 행의 시간 간격"으로 나누면 깔끔하게 갈립니다.

실제 간격 분포가 그것을 보여줍니다:

| 백분위 | 간격 |
|---|---|
| 50% | 54 ms |
| 60% | 288 ms |
| **62%** | **4.6 초** ← 절벽 |
| 65% | 46 초 |
| 70% | 120 초 |
| 80% | 13 일 |

**5초와 46초 사이에는 사실상 아무것도 없습니다.** 그래서 어디를 잘라도
답이 거의 같습니다:

| 묶는 기준 | 도착 횟수 |
|---|---|
| 200 ms | 102 |
| 500 ms | 92 |
| 1 초 | **91** |
| 2 초 | **91** |
| 5 초 | 90 |
| 10 초 | 88 |

500ms에서 5초까지 90~92로 평평합니다. **91**을 쓰시면 됩니다.

한 번의 방문이 만든 행 수 분포 (2초 기준):

| 행/방문 | 방문 수 |
|---|---|
| 1 | 23 |
| 2 | 31 |
| 3 | 5 |
| **4** | **28** |
| 5 | 1 |
| 6 | 2 |
| 8 | 1 |

2개가 아니라 4개인 경우가 28번으로 많습니다. 부팅 시 사용자를 묻는 화면
수가 어느 화면에 착지했는지에 따라 달라지기 때문으로 보입니다 — 이 부분은
추론이고, 당시 배포본을 재현해 확인한 것은 아닙니다.

## 5. 91도 "이용자 수"는 아닙니다 — 반드시 읽어주세요

91은 **브라우저 도착 횟수**입니다. 사람 수가 아닙니다. 위로도 아래로도
틀릴 수 있습니다:

- **과대 계상** — 한 사람이 폰과 노트북으로 열면 2, 쿠키를 지우면 또 1,
  시크릿 창도 각각 1입니다.
- **과대 계상** — **개발·테스트 접속이 섞여 있습니다.** 8/30, 8/31, 9/1의
  수치에는 저희가 확인용으로 연 것들이 포함돼 있습니다. 9/1의 5회는
  대부분 오늘 이 버그를 재현하고 검증하느라 연 것입니다.
- **과대 계상 — UI 검증 과정의 자동 접속이 다수 포함돼 있고, 정확한 수는
  모릅니다.** 9/1 하루에만 RLS 정책·좌석 수·여성 필터를 확인하느라 저장소를
  여러 번 비우고 앱을 새로 열었고, 그때마다 익명 계정이 하나씩 생겼습니다.
  확인된 것은 `4b63bd6c-75d6-467c-883c-bb198b2be807`와 `cb6b50ab-…` 둘이지만
  **그게 전부라는 근거는 없습니다.** 세어 두지 않았기 때문에 사후에 사람의
  방문과 구분할 방법이 없고, 추정치를 지어내는 것보다 모른다고 적는 편이
  정직합니다.
- **과소 계상** — 같은 브라우저로 여러 날 온 사람은 1로 셉니다.

**결과보고서에 쓰실 때 권장 표현:**

> 시범운영 기간 중 접속 세션 약 91건 (2026-08-03 ~ 09-01, 브라우저 기준.
> 개발·테스트 접속 및 UI 검증 과정의 자동 접속 다수 포함, 정확한 수 미상)

"이용자 237명"은 쓰지 마세요. 사실이 아닙니다.

진짜 참가자 수를 세시려면 `profiles`가 아니라 **`signups`(밥상에 자리를
청한 기록)** 나 **`member_details`(실제 가입한 회원)** 를 세는 게 맞습니다.
그 두 테이블은 이 버그의 영향을 받지 않습니다 — 사람이 직접 행동해야 생기는
행이라서요.

## 6. 행은 지우지 않았습니다

집계만 했습니다. 고아 행을 지우려면 `auth.users`까지 함께 지워야 하고
(외래키), 되돌릴 수 없습니다. 결과보고서 숫자만 정확하면 되는 일이라면
지울 이유가 없습니다.

지우기로 결정하신다면 그때 별도로 SQL을 검토해서 드리겠습니다.

### 제외 목록을 뺀 실제 참가자 수

`profiles`를 세지 마세요 — §5에서 쓴 이유 그대로입니다. 사람이 직접
행동해야만 생기는 두 테이블을 셉니다. 아래 쿼리는 위 표의 uuid를 뺀
숫자를 냅니다. **표에 줄을 추가하면 `excluded`에도 추가해야 합니다.**

```sql
with excluded (id) as (values
  ('4b63bd6c-75d6-467c-883c-bb198b2be807'::uuid),
  ('cb6b50ab-3877-4aa1-85fe-b5a415e6d6da'::uuid),
  ('19f6ab00-1a17-4567-a40d-851c61025884'::uuid),
  ('39edcb02-3928-4190-943b-d318584fd621'::uuid),
  ('9706ff0f-7f69-422b-acc7-901b4a2aa980'::uuid)
)
select
  (select count(*) from public.profiles)                                as profiles_all,
  (select count(*) from public.profiles
    where id not in (select id from excluded))                          as profiles_minus_known_dev,
  -- 실제로 쓸 숫자는 아래 둘입니다.
  (select count(distinct user_id) from public.signups
    where user_id not in (select id from excluded))                     as people_who_asked_for_a_seat,
  (select count(*) from public.member_details
    where id not in (select id from excluded) and email <> '')          as members_with_an_email,
  -- 취소한 요청도 사람이 한 행동이므로 위 숫자에 포함됩니다.
  -- 취소를 빼고 싶으면 이쪽을 쓰세요 (2026-09-01e 이후에만 의미가 있습니다).
  (select count(distinct user_id) from public.signups
    where cancelled_at is null
      and user_id not in (select id from excluded))                     as people_holding_a_live_seat
from (select 1) _;
```

`profiles_minus_known_dev`는 **참가자 수가 아닙니다.** 표에 적힌 것만
빼기 때문에, 적어두지 않은 개발 접속은 그대로 남아 있습니다. 아래를
읽어주세요.

### 지금까지 쌓인 dev 세션을 사후에 골라낼 수 있나 — 없습니다

찾아본 결과를 그대로 적습니다. **`profiles`만으로는 구분할 방법이
없습니다.** 개발 접속이 남기는 행과, 그냥 둘러보고 나간 진짜 방문자가
남기는 행이 **모든 칸에서 똑같습니다**:

| 칸 | 개발 접속 | 둘러보고 나간 방문자 |
|---|---|---|
| `name` | 비어 있음 | 비어 있음 |
| `nationality` | 비어 있음 | 비어 있음 |
| `languages` | `{}` | `{}` |
| `gender` | null | null |
| `rules_version` / `rules_agreed_at` | null | null |
| `signups` 행 | 없음 | 없음 |
| `member_details` 행 | 없음 | 없음 |

`created_at`도 갈라주지 못합니다. 8/30~9/1은 개발이 몰린 날이면서 동시에
2차 시범운영이 시작된 구간이라, 시간대로 자르면 진짜 참가자를 지웁니다.
§3에서 쓴 밀리초 간격 기법은 "한 번의 방문이 만든 여러 행"을 묶는
것이지, 그 방문이 누구였는지는 말해주지 않습니다.

한 가지 남은 가능성은 Supabase의 인증 감사 로그(`auth.audit_log_entries`)에
요청 IP가 남는지 여부입니다. 남는다면 팀 IP로 걸러낼 수 있습니다. 다만
**저는 이것을 확인하지 않았고, 확인을 권하지도 않습니다** — 그 테이블을
읽는다는 것은 참가자 전원의 IP를 함께 읽는다는 뜻이고, 보고서의 숫자
하나를 위해 치를 값이 아닙니다. 보존 기간도 짧아서 8월 초 세션은 이미
없을 가능성이 큽니다.

**그래서 답은: 지금까지 것은 모릅니다.** 추정치를 만들지 않았습니다.
§5의 표현("개발·테스트 접속 다수 포함, 정확한 수 미상")을 그대로 쓰시고,
앞으로 것은 위 표에 적어서 정확히 셉니다.

### 근본 해결은 별건입니다

dev 전용 Supabase 프로젝트를 따로 만들고 `.env.local`을 그쪽으로 돌리면
이 문제가 사라집니다. **규모: 한 시간 남짓** — 프로젝트 생성, `schema.sql`

### 재동의 대상 — 두 숫자, 섞지 마세요

**추가 2026-09-02.** 동의 문구 개정(`PURPOSE.version` 1→2) 앞서 잰 것입니다.

네 숫자를 나란히 놓은 표는 §0에 있습니다. 여기서는 뒤의 세 개만 다룹니다.

| 값 | 어디에 쓰는가 |
|---|---|
| **10** — `rules_version is not null`인 프로필 전부 | `2026-09-02a` 마이그레이션의 `backfilled_rows` **합격값**. 제외 없이 전부입니다 — 이력은 개발 접속까지 포함해 "실제로 그 행이 동의했다"는 기록이라, 여기서 빼면 이력이 거짓이 됩니다 |
| **10 − 제외 목록 중 동의한 행** | KF 보고서 **"동의 문구 개정, 재동의 대상 N명"**. 제외 목록(§7 표)의 계정이 게이트를 눌렀다면 그만큼 뺍니다 |

두 번째 값은 아래로 냅니다. 행 내용은 열지 않습니다. 표에 줄을 추가하면 `excluded`에도 추가해야 합니다.

```sql
with excluded (id) as (values
  ('4b63bd6c-75d6-467c-883c-bb198b2be807'::uuid),
  ('cb6b50ab-3877-4aa1-85fe-b5a415e6d6da'::uuid),
  ('19f6ab00-1a17-4567-a40d-851c61025884'::uuid),
  ('39edcb02-3928-4190-943b-d318584fd621'::uuid),
  ('9706ff0f-7f69-422b-acc7-901b4a2aa980'::uuid)
)
select
  count(*) filter (where rules_version is not null)                                   as agreed_all,       -- 마이그레이션 합격값
  count(*) filter (where rules_version is not null and id in (select id from excluded)) as agreed_dev,       -- 그중 개발 접속
  count(*) filter (where rules_version is not null and id not in (select id from excluded)) as agreed_for_kf -- KF 보고서 값
from public.profiles;
```

`39edcb02`와 `9706ff0f`는 오늘 확인 과정에서 동의 게이트를 눌렀으므로 `agreed_dev`에 최소 2가 잡혀야 정상입니다. 그보다 작게 나오면 표가 틀린 것입니다.

**실측 2026-09-02: `agreed_all` 10 · `agreed_dev` 2 · `agreed_for_kf` 8.** 반증 조건을
통과했습니다 — 표에 적힌 두 계정이 실제로 잡혔습니다.

### 8도 참가자 수가 아닙니다 — 제외 목록이 불완전합니다

표는 살아 있지만 **완전하지는 않습니다.** 표에는 다섯 개가 있고, 앱을 써 본 팀원은
그보다 많습니다. 같은 날 라이브의 밥상 3개와 좌석 신청 2건이 전부 팀 계정이었으니,
사람이 직접 행동해야 생기는 행조차 아직 팀이 만든 것뿐입니다.

목록을 넓힐 근거는 아래로 찾습니다. **uuid는 출력하지 않습니다** — 개수만 봅니다.

```sql
with excluded (id) as (values
  ('4b63bd6c-75d6-467c-883c-bb198b2be807'::uuid),
  ('cb6b50ab-3877-4aa1-85fe-b5a415e6d6da'::uuid),
  ('19f6ab00-1a17-4567-a40d-851c61025884'::uuid),
  ('39edcb02-3928-4190-943b-d318584fd621'::uuid),
  ('9706ff0f-7f69-422b-acc7-901b4a2aa980'::uuid)
), kf as (
  select id from public.profiles
   where rules_version is not null and id not in (select id from excluded)
)
select
  (select count(*) from kf)                                                     as agreed_for_kf,
  (select count(*) from kf where id in (select host_id from public.tables))      as of_those_hosted,
  (select count(*) from kf where id in (select user_id from public.signups))     as of_those_asked_for_a_seat;
```

라이브의 밥상과 신청이 전부 팀 것이라면 뒤의 두 값은 **0**이어야 합니다. 0이 아니면
그 수만큼 팀 계정이 제외 목록 밖에 있다는 뜻이고, 그때는 8을 쓰기 전에 표부터
넓힙니다.

### 실측 2026-09-02 — 제외 목록은 불완전합니다

`agreed_for_kf` **8** · `of_those_hosted` **3** · `of_those_asked_for_a_seat` **2**.

> **8은 동의 문구 개정으로 재동의가 필요한 프로필 수다. 이 중 3이 밥상을 열었고
> 2가 자리를 신청했으며, 알려진 밥상 3·신청 2가 모두 팀 계정이므로 그 3~5는 팀이다.
> 제외 목록(5건)은 불완전하다. 참가자 수로 쓸 수 있는 숫자는 이 표에 없다.**

라이브의 밥상은 전부 3개, 좌석 신청은 전부 2건이고 둘 다 전부 팀 계정입니다. 그
3과 2가 통째로 8 안에 들어 있습니다. 따라서 제외 목록 밖에 팀 계정이 **최소 3,
많으면 5** 더 있습니다.

8에서 그것을 뺀 나머지는 **동의만 누르고 밥상도 열지 않고 신청도 하지 않은
프로필**입니다. 어느 쪽이든 **실제로 한 상에 앉은 사람은 0명입니다.**

이 문단은 숫자를 깎으려고 쓴 것이 아닙니다. 8을 "참가자 8명"으로 옮겨 적을 수
있는지 물으면 답이 아니오라는 것을, 문서가 스스로 말하게 하려고 적었습니다.
