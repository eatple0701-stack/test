# 파일럿 이용자 수 — `profiles` 행 수를 그대로 쓰면 안 되는 이유

**작성 2026-09-01.** 결과보고서(9/20)에 이용자 수를 쓰실 분에게 넘기는 자료입니다.

> **결론부터**: `profiles` 테이블에 **237행**이 있지만, 실제 도착 횟수는
> **약 91회**입니다. 행 수를 그대로 쓰면 **2.6배 부풀린 숫자**를 KF에
> 보고하게 됩니다.

---

## 1. 무슨 일이 있었나

2026-07-29부터 2026-09-01까지, 앱은 **첫 방문 한 번에 익명 계정을 여러 개**
만들었습니다.

부팅 중에 여러 화면이 동시에 "지금 사용자가 누구냐"를 묻는데, 첫 방문이면
전부 "세션 없음"을 보고 전부 익명 로그인을 호출했습니다. 호출된 만큼 계정이
생기고, 그만큼 `profiles` 행이 생깁니다. 토큰은 하나만 남으므로 나머지는
**아무도 돌아갈 수 없는 고아 행**입니다.

- 유입: `1aac1cd` (2026-07-29) — 처음 작성될 때부터
- 수정: `eff119f` (2026-09-01)
- 실제 데이터가 쌓인 구간: **2026-08-03 ~ 2026-09-01**
  (첫 행이 8/3이므로 7/29~8/2에는 트래픽이 없었습니다)

수정 후 프로덕션 실측: 첫 방문 → 로그인 1회, 행 1개.

## 2. 숫자

| | |
|---|---|
| `profiles` 총 행 수 | **237** |
| 추정 실제 도착 횟수 | **약 91** |
| 고아 행 | 약 146 |
| 부풀림 배율 | **약 2.6배** |

## 3. 어떻게 셌나

행 삭제는 하지 않았습니다. **`created_at` 타임스탬프만** 읽어서 세었습니다
(이름·국적·언어는 조회하지 않았습니다).

같은 페이지 로드에서 만들어진 계정들은 **밀리초 단위로 붙어서** 생성됩니다.
반면 서로 다른 방문은 최소 수십 초, 보통 몇 시간에서 며칠 떨어져 있습니다.
그래서 "연속한 두 행의 시간 간격"으로 나누면 깔끔하게 갈립니다.

실제 간격 분포가 그것을 보여줍니다:

| 백분위 | 간격 |
|---|---|
| 50% | 54 ms |
| 60% | 288 ms |
| **62%** | **4.6 초** ← 절벽 |
| 65% | 46 초 |
| 70% | 120 초 |
| 80% | 13 일 |

**5초와 46초 사이에는 사실상 아무것도 없습니다.** 그래서 어디를 잘라도
답이 거의 같습니다:

| 묶는 기준 | 도착 횟수 |
|---|---|
| 200 ms | 102 |
| 500 ms | 92 |
| 1 초 | **91** |
| 2 초 | **91** |
| 5 초 | 90 |
| 10 초 | 88 |

500ms에서 5초까지 90~92로 평평합니다. **91**을 쓰시면 됩니다.

한 번의 방문이 만든 행 수 분포 (2초 기준):

| 행/방문 | 방문 수 |
|---|---|
| 1 | 23 |
| 2 | 31 |
| 3 | 5 |
| **4** | **28** |
| 5 | 1 |
| 6 | 2 |
| 8 | 1 |

2개가 아니라 4개인 경우가 28번으로 많습니다. 부팅 시 사용자를 묻는 화면
수가 어느 화면에 착지했는지에 따라 달라지기 때문으로 보입니다 — 이 부분은
추론이고, 당시 배포본을 재현해 확인한 것은 아닙니다.

## 5. 91도 "이용자 수"는 아닙니다 — 반드시 읽어주세요

91은 **브라우저 도착 횟수**입니다. 사람 수가 아닙니다. 위로도 아래로도
틀릴 수 있습니다:

- **과대 계상** — 한 사람이 폰과 노트북으로 열면 2, 쿠키를 지우면 또 1,
  시크릿 창도 각각 1입니다.
- **과대 계상** — **개발·테스트 접속이 섞여 있습니다.** 8/30, 8/31, 9/1의
  수치에는 저희가 확인용으로 연 것들이 포함돼 있습니다. 9/1의 5회는
  대부분 오늘 이 버그를 재현하고 검증하느라 연 것입니다.
- **과대 계상 — UI 검증 과정의 자동 접속이 다수 포함돼 있고, 정확한 수는
  모릅니다.** 9/1 하루에만 RLS 정책·좌석 수·여성 필터를 확인하느라 저장소를
  여러 번 비우고 앱을 새로 열었고, 그때마다 익명 계정이 하나씩 생겼습니다.
  확인된 것은 `4b63bd6c-75d6-467c-883c-bb198b2be807`와 `cb6b50ab-…` 둘이지만
  **그게 전부라는 근거는 없습니다.** 세어 두지 않았기 때문에 사후에 사람의
  방문과 구분할 방법이 없고, 추정치를 지어내는 것보다 모른다고 적는 편이
  정직합니다.
- **과소 계상** — 같은 브라우저로 여러 날 온 사람은 1로 셉니다.

**결과보고서에 쓰실 때 권장 표현:**

> 시범운영 기간 중 접속 세션 약 91건 (2026-08-03 ~ 09-01, 브라우저 기준.
> 개발·테스트 접속 및 UI 검증 과정의 자동 접속 다수 포함, 정확한 수 미상)

"이용자 237명"은 쓰지 마세요. 사실이 아닙니다.

진짜 참가자 수를 세시려면 `profiles`가 아니라 **`signups`(밥상에 자리를
청한 기록)** 나 **`member_details`(실제 가입한 회원)** 를 세는 게 맞습니다.
그 두 테이블은 이 버그의 영향을 받지 않습니다 — 사람이 직접 행동해야 생기는
행이라서요.

## 6. 행은 지우지 않았습니다

집계만 했습니다. 고아 행을 지우려면 `auth.users`까지 함께 지워야 하고
(외래키), 되돌릴 수 없습니다. 결과보고서 숫자만 정확하면 되는 일이라면
지울 이유가 없습니다.

지우기로 결정하신다면 그때 별도로 SQL을 검토해서 드리겠습니다.
