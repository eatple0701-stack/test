## 1 — `profiles` + `signups` (오늘)

`supabase/migrations/2026-09-01b-scope-profile-reads-retry.sql`

### 순서가 중요합니다

**클라이언트를 먼저 배포하고, 그다음 SQL을 실행하세요.** 반대로 하면 낯선
방문자의 좌석 수가 전부 0으로 보입니다 — 오늘은 그게 마침 참값이지만, 첫
신청이 들어오는 순간 거짓이 됩니다.

### SQL

편집기에 **그대로 붙여넣고 실행**하세요. 마지막 줄이 `rollback;`이라 아무것도
안 바뀝니다. 정책을 적용해 보고, 낯선 방문자·평범한 회원·실제 호스트 세 사람의
눈으로 읽어보고, 숫자를 찍고, 전부 버립니다.

```
stranger_sees_profiles   한 자릿수
member_sees_own_row      1      ← 가장 중요한 줄
member_sees_profiles     한 자릿수
host_sees_own_row        1
host_sees_profiles       한 자릿수
stranger_sees_signups    0
seat_holds_visible       signups_total 과 같음
```

전부 참이면 **마지막 줄 `rollback;`을 `commit;`으로 바꿔 다시 실행**하세요.
재귀하면 트랜잭션이 중단되어 42P17만 뜨고 숫자표는 안 나옵니다 — 어느 쪽이든
운영 DB는 지금 정책을 그대로 유지합니다.

### signups를 같은 파일에 넣은 이유

처음엔 뺐습니다. 근거는 맞았지만 결론이 틀렸습니다 — `signups`가 **아직
0행**이라 지금 닫으면 공짜입니다. 좌석 수가 어차피 0이니까요. 첫 신청이
들어오는 순간 이름·국적·자유 note가 `using(true)` 아래 놓이고, 그때부터 닫는
것은 화면에서 뭔가를 빼앗는 변경이 됩니다. **지금이 유일한 창입니다.**

막고 있던 것은 집계 하나였고, 작습니다:

- `seat_holds()` — 잡힌 좌석마다 한 행, **밥상 id와 상태만.** 사용자
  id·이름·국적·note·성별 없음. 거절된 요청은 아예 안 나갑니다(호스트가 몇 명을
  돌려보냈는지 세어지면 안 되니까).
- 총계가 아니라 상태를 돌려주는 이유: 대기 중 요청은 **자리는 차지하지만
  동석자는 아닙니다.** 카드 위의 두 숫자가 다릅니다. SQL에서 합계를 내면 그
  규칙이 `seatRequest.js`와 두 곳에 살게 되고, 사본은 어긋납니다.
- 클라이언트는 읽을 수 없는 밥상에 한해 **익명 자리**로 채웁니다
  (`src/domain/policy/seatHolds.js`). `signups_read`는 한 밥상의 행을 전부
  주거나 전혀 안 주므로 "못 읽었다"와 "없다" 두 경우만 존재합니다 — 그래서
  밥상 단위 병합이 정확합니다.

### 열린 호스트 조건에 30일 창을 넣었습니다

`cancelled_at is null`만으로는 **한 번이라도 연 사람이 영구 공개**입니다.
파일럿이 커지면 역대 모든 호스트가 영구 공개가 되고, 노출은 줄지 않고 늘기만
합니다.

이름을 공개하는 근거는 **지금 열려 있는 초대**이고, 그 근거는 밥상과 함께
끝납니다. `>= current_date`가 아니라 30일인 이유는 카카오톡에 공유된 링크가
저녁보다 오래 살기 때문입니다.

잃는 것은 없습니다 — 지난 밥상·취소된 밥상의 손님은 `shares_a_table`로 그
호스트를 계속 읽습니다. **거기엔 기한이 없습니다. 자기 저녁은 자기 것입니다.**

### 어제와 무엇이 다른가

어제 실패한 이유는 SQL이 틀려서가 아니라 **아무도 돌려본 적이 없어서**입니다.
테스트 다섯 개가 전부 SQL의 *글자*만 봤습니다.

이번엔 돌려봤습니다. `@electric-sql/pglite`(Postgres 18을 wasm으로 컴파일한
것)를 devDependency로 넣고, `src/domain/__tests__/rlsPolicies.test.mjs`가
**마이그레이션 파일을 그대로 실행**합니다. 237행 픽스처, 실제 플래너, 실제 RLS.
클라이언트 번들에는 안 들어갑니다.

첫 번째 테스트가 제일 중요합니다 — **어제 죽은 정책을 적용해서 여기서도
42P17이 나는지** 확인합니다. 하네스가 그 실패를 재현하지 못하면 나머지 단언은
전부 장식입니다.

일부러 깨뜨리기 19종, 전부 RED. 그중 셋은 처음에 GREEN이었고 진짜 구멍이었습니다:

- **본인 행 읽기**를 호스트로만 확인하고 있었습니다. 호스트는 `is_open_host`로
  어차피 보이니, 정책에서 `id = auth.uid()`를 통째로 지워도 통과했습니다.
  어제 프로덕션을 죽인 증상이 바로 그건데 테스트가 못 봤습니다.
  → 밥상도 신청도 없는 평범한 회원(237명 중 235명)으로 확인하게 고쳤습니다.
- **취소된 밥상의 호스트**를 볼 손님이 픽스처에 없어서, `shares_a_table`의
  호스트-손님 갈래를 끊어도 다른 갈래가 덮었습니다.
- 헬퍼가 0행을 돌려줄 때 앞 문장의 결과셋을 집어오는 버그가 있어서 "아무것도
  못 본다" 계열 단언이 0 대신 1을 읽고 있었습니다. 두 테스트가 공허했습니다.

픽스처 날짜도 상대값으로 바꿨습니다 — 30일 창이 생겼으니 고정 날짜였다면 한 달
뒤 이 파일이 조용히 아무것도 검사하지 않게 됩니다.

## 2 — `tables` 공개 뷰

### 공개 — 밥상의 진열창

```
id  menu_id  host_id  host_name  host_verified  host_kind
date  time  place  restaurant  seats  note  guides  languages
lat  lng  cancelled_at  created_at
```

`lat`/`lng`은 공개로 둡니다. `place`("홍대입구 3번 출구")가 이미 공개라 좌표가
새 정보를 더하지 않고 정밀도만 올립니다.

`host_name`은 목록에서도 보입니다. `safetyPromise.js` 첫 항목이 *"청하기 전에
호스트가 누구인지 봅니다"*이고, 그 파일은 앱이 실제로 하는 것만 적는다는 규칙
아래 있습니다. 가리면 문서가 거짓이 됩니다.

### 밥상에 앉은 사람만

```
chat_url        모임 채팅방 주소
meeting_note    "빨간 가방 들고 있을게요" — 특정인을 알아보는 법
host_nationality
is_sample       내부 플래그. 공개할 이유 없음
host_gender     아예 안 나감 (필터는 서버에서 — 위 1번에서 이미 처리됨)
```

앞의 둘은 좌표·시각과 합쳐지면 **특정 개인에게 접근하는 방법**이 됩니다. UI는
이미 이 둘을 게이트하고 있고 데이터만 안 하고 있습니다.

`host_nationality`는 공개 화면 어디에도 렌더되지 않습니다 — 여권(본인 기록)에만
나옵니다.

`chat_url`의 스키마 주석은 이 노출을 이미 알고 허용한다고 적어 두었습니다:

> "an API reader can see it, which is acceptable for a link the host chose to
> share with strangers they invited."

그 판단을 뒤집습니다. 집합이 다릅니다 — 호스트가 공유하기로 한 대상은 *자기가
초대한 사람들*이고, 실제로 읽을 수 있는 대상은 *anon 키를 가진 누구나*입니다.
anon 키는 모든 번들에 들어갑니다. **지금은 아직 이론입니다** — 밥상 2건 모두
`chat_url`이 비어 있습니다. 호스트가 하나 넣는 순간 실제가 됩니다.

### `has_woman`을 공개 컬럼으로 내보내지 않는 이유

처음 제안은 파생 불리언을 공개 뷰에 두는 것이었고, 그건 틀렸습니다.

`seats: 4`에 참가자가 둘이고 아바타·이름이 보이는 상태에서 `has_woman = true`면
**나머지 한 명이 특정됩니다.** 작은 집단에 대한 파생값은 원본 속성만큼 샙니다.

더 나쁜 건 시간입니다. 누가 신청한 직후 `false → true`로 뒤집히면 **그 사람의
성별을 정확히 지목한 것**이 됩니다. 정적 속성보다 나쁜 유출입니다.

그래서 파생값을 내보내지 않고 **필터를 서버에서 적용**합니다. 위 1번의
`tables_with_woman()`이 그것이고, 필터를 켰을 때만 호출됩니다.

### 순서

1. 뷰 생성 + grant — **추가만 하므로 아무것도 안 깨짐**
2. 클라이언트를 뷰로 전환해 배포 (목록은 뷰, 상세는 원본)
3. 원본 `tables`의 select 조이기

3단계만 되돌리면 언제든 지금 상태로 복귀합니다.

## `note` — 위험은 읽기가 아니라 쓰기에 있습니다

`tables.note`는 공개 유지입니다. 호스트가 밥상을 설명하는 글이라 신청 전에
읽어야 결정할 수 있고, 숨기면 판단 자체가 불가능해집니다.

문제는 **자유 입력인데 보호가 없다**는 것입니다. `meeting_note`를 잠그는
이유(연락처·상세 주소가 적힐 수 있음)가 `note`에도 똑같이 있습니다.

RLS로 풀 문제가 아니라 **작성 화면에서 풀 문제**입니다:

- 입력란에 "누구나 볼 수 있어요" 라벨
- 전화번호 · 카카오톡 ID · 상세 주소 패턴이 들어가면 경고
  (막지는 않음 — 호스트의 글이고, 경고는 정보이지 검열이 아님)

`signups.note`는 다릅니다. 호스트에게 쓰는 글이므로 **호스트 + 본인만** 유지 —
위 1번의 `signups_read`가 이미 그렇게 합니다.

## 별건 — `host_verified` / `host_kind`가 비어 있는 것

두 밥상 다 `host_verified: false`, `host_kind: null`입니다. 확인 결과:

**안전 섹션의 약속은 지켜지고 있습니다.** `safetyPromise.js`가 약속하는 것은
*"이름, 할 수 있는 언어, 그리고 지금까지 실제로 연 밥상 수"*이고, 그 셋째는
`host_verified`가 아니라 `tablesHosted`입니다 — `hostRecord()`가 실제 밥상 행을
세어 계산합니다(`supabaseBackend.js:647`). 처음이면 "처음"이라고 나옵니다.

**대신 다른 게 나왔습니다. `host_verified`를 켜는 코드가 어디에도 없습니다.**

- `tableToRow()`는 `profiles.is_verified_host`를 복사합니다
  (`supabaseBackend.js:285`).
- 그런데 `is_verified_host`에 `true`를 쓰는 코드가 레포 전체에 없습니다.
  읽기만 있습니다.
- 스키마 주석도 "set out of band, by whoever did the checking"이라고 적어
  두었습니다 — 즉 **대시보드에서 손으로 켜는 것이 설계**입니다.

결과 두 가지:

1. `TablesTab.jsx`의 **"인증 · verified" 배지와 `hostKindLabel`은 지금 절대
   안 뜹니다.** 죽은 UI이지 깨진 약속은 아닙니다.
2. **더 실질적인 것:** 값이 밥상을 만드는 순간 복사됩니다. 팀이 나중에 프로필을
   인증해도 **이미 만들어진 밥상은 계속 `false`입니다.** 인증 제도를 실제로 쓸
   거라면 이건 고쳐야 합니다 — 복사 대신 조인이거나, 인증 시 기존 행을 갱신하거나.

지금 파일럿에서 인증 호스트를 쓸 계획이 없으면 그대로 둬도 됩니다.
